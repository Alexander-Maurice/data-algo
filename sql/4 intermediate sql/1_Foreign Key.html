Foreign Key

Чему вы научитесь

  1. Что такое внешний ключ и для чего он используется.
  2. Как настроить различные механизмы защиты данных внешним ключом.

Какие проблемы могут решить внешние ключи?

Поздравляем с переходом в более продвинутые главы!

В первой главе будет интерпретироваться концепция FOREIGN KEY, о которой мы упоминали в предыдущих главах. Фактически внешний ключ — это столбец привязки внешних данных, таких как user_id, order_id, который мы установили в прошлом.

Раньше мы записывали данные в относительных столбцах и использовали свой мозг, чтобы определить, связаны ли они. Но на практике мы можем установить CONSTRAINT для внешнего ключа через SQL, чтобы помочь нам выполнять автоматические проверки и защищать безопасность данных.

Что такое безопасность данных? Давайте представим ситуацию, когда у клиента есть большой объем данных о заказе, но однажды инженер по ошибке удаляет данные о заказе клиента. Таким образом, если кому-то понадобится узнать об истории заказов клиента в будущем, он не будет знать, что удаленные заказы принадлежат этому клиенту. Это катастрофа в бизнесе.

К счастью, с помощью FOREIGN KEY мы можем автоматически и эффективно избежать таких проблем. Давайте посмотрим, как его использовать!

Sample table

users

id name age
1 John 40
2 May 30
3 Jack 22

orders

id user_id note
1 1 some information
2 2 some comments
3 2 no comments
4 3 more comments

Основной синтаксис и использование

Для таблицы необходимо настроить внешний ключ, поэтому ключевые слова ALTER TABLE необходимо использовать следующим образом:

ALTER TABLE `new_schema`.`orders`
ADD CONSTRAINT `orders_user_id_key`
FOREIGN KEY (`user_id`)
REFERENCES `new_schema`.`users` (`id`);

Здесь мы можем разделить его на четыре части:
1. ALTER TABLE: Мы уже использовали этот оператор несколько раз; этот оператор указывает, какую таблицу установить.
2. ADD CONSTRAINT: оно указывается перед именем ограничения, которое вы хотите добавить. Мы устанавливаем order_user_id_key в качестве имени ограничения.
3. FOREIGN KEY: относится к внешнему ключу, который вы хотите связать. Мы устанавливаем user_id в этой таблице в качестве нашего внешнего ключа.
4. REFERENCES: Укажите таблицу внешних данных, к которой привязан внешний ключ. Мы устанавливаем его в столбец id в таблице users.

Защита от УДАЛЕНИЯ

Если после выполнения предыдущего оператора мы попытаемся выполнить оператор удаления для удаления пользователя:

DELETE FROM `new_schema`.`users` WHERE (`id` = '1');

Если мы попытаемся выполнить эту команду, появится подобное сообщение об ошибке, которое не позволит нам удалить пользователя:

ERROR 1451: 1451: Cannot delete or update a parent row: a foreign key constraint fails

Причина этого сообщения в том, что пользователь с идентификатором 1 был привязан к столбцу user_id некоторых записей в таблице orders. Это выполнение запускает механизм защиты, предотвращая тем самым проблему отсутствия данных.

Protection from UPDATE

Другой сценарий, предполагающий, что мы не удаляем данные, а обновляем внешний ключ исходных данных users, также активирует ограничение, имеющее механизм защиты данных. Например:

UPDATE `new_schema`.`users` SET `id` = '6' WHERE (`id` = '1');

Мы получим то же сообщение об ошибке:

ERROR 1451: 1451: Cannot delete or update a parent row: a foreign key constraint fails

Причина ошибки заключается в том, что мы хотим изменить пользователя с идентификатором 1 и обновить его идентификатор до 6, что приведет к тому, что соответствующие записи заказа найдут неподходящего пользователя и выдадут ошибку. Итак, наши ограничения срабатывают, чтобы спасти нас.

Однако если мы выполним следующие инструкции, ошибки выполнения не возникнет:

UPDATE `new_schema`.`users` SET `name` = 'Tony' WHERE (`id` = '1');
UPDATE `new_schema`.`orders` SET `user_id` = '3' WHERE (`id` = '1');

Причина в том, что выполненный нами SQL не нарушает логическую корректность ограничения. Мы изменяем только значение в других столбцах, таких как name, или обновляем запись относительного users на другую, например Jack.

Remove a Constraint

Поскольку мы можем создать ограничение, мы также должны иметь возможность его удалить. Синтаксис удаления следующий:

ALTER TABLE `new_schema`.`orders`
DROP FOREIGN KEY `orders_user_id_key`;

Стоит отметить, что если вы хотите обновить ограничение, вам необходимо сначала удалить ограничение, а затем добавить новое ограничение. Относительного оператора обновления нет.

Разнообразные ограничения

В SQL существуют различные режимы ограничений, и мы можем устанавливать ограничения индивидуально для действий UPDATE и DELETE.

Помимо настроек различного поведения, вы также можете установить режимы. Как и в предыдущем примере, если вы не укажете режим при создании ограничения, режимом по умолчанию будет NO ACTION.

NO ACTION эквивалентен режиму RESTRICT в MySQL. Как мы заметили, этот режим защищает данные, запрещая реализацию UPDATE и DELETE, когда команда не подчиняется ограничению. Если вы знакомы с другими системами баз данных SQL, рекомендуем проверить подробности в соответствующих официальных документах! Но обычно эти функции одинаковы для каждой системы баз данных.

Синтаксис

В синтаксической части вы можете установить режимы различного поведения следующим образом:

ALTER TABLE `new_schema`.`orders`
ADD CONSTRAINT `orders_user_id_key`
FOREIGN KEY (`user_id`)
REFERENCES `new_schema`.`users` (`id`)
ON DELETE NO ACTION
ON UPDATE RESTRICT;

Вы можете сосредоточиться на двух новых фразах ON DELETE и ON UPDATE. С помощью этих двух фраз можно установить режим для DELETE и UPDATE, а название режима можно добавить непосредственно после фраз.

Ссылочные действия

В ограничении официальное название NO ACTION & RESTRICT называется «Ссылочные действия», и эти действия широко используются. В дополнение к этому SQL обычно предоставляет следующие два других режима:

  1. CASCADE: динамическая настройка внешнего ключа другой таблицы при срабатывании ограничения. Например, если идентификатор пользователя изменен на 6, user_id соответствующих записей заказа также будет обновлен до 6 вместе.
  2. SET NULL: вы можете динамически устанавливать для внешнего ключа другой таблицы значение NULL при возникновении такого поведения. Например, если идентификатор пользователя изменен на 6, user_id, соответствующий записям заказов, будет изменен на ноль.
